# Release packaging

The GitHub Actions workflow in `.github/workflows/build.yml` builds and validates
both desktop targets:

- **Windows 10/11 x64**: portable archive and Inno Setup installer (`.exe`).
- **Linux x64**: Debian package (`.deb`) built on Ubuntu 22.04.

## Release flow

Push a tag such as `v0.1.0` after the build workflow is green:

```bash
git tag v0.1.0
git push origin v0.1.0
```

The tag run builds both platforms, then publishes a GitHub Release containing:

| Asset | Purpose |
| --- | --- |
| `Concord-<version>-windows-x64-setup.exe` | Windows installer |
| `Concord-<version>-windows-x64-portable.zip` | Windows portable build |
| `concord_<version>_amd64.deb` | Ubuntu/Debian package |
| `downloads.json` | Stable machine-readable download manifest |
| `SHA256SUMS.txt` | Checksums for every release asset |

`downloads.json` is intended for the future landing page. The stable URL is:

```text
https://github.com/luizhmmachado/Concord/releases/latest/download/downloads.json
```

It contains the version, release URL, per-platform requirements, direct download
URLs, sizes and SHA-256 hashes. Use the versioned asset URLs from that file rather
than hard-coding filenames in the landing page.

## Runtime dependencies

- **Windows**: the release bundles Qt and the GStreamer runtime. The installer is
  per-user and does not require a separate GStreamer installation.
- **Linux**: the `.deb` depends on the distribution's Qt 5.15 and GStreamer 1.20+
  packages, listed in the `Depends` field generated by
  `packaging/linux/build-deb.sh`.

## Signing and future targets

Windows code signing and Linux repository signing are not configured yet. Add
those secrets to the release job before promoting builds to a wide audience.
Additional targets (AppImage, arm64, macOS) can reuse the same release contract
and add new entries to `downloads.json`.
